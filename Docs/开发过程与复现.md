## 1. 起点：把手册的四个脚本做成一个完整游戏

> **我**：`@Unity4K音游制作手册.doc` 按照这个帮我把我的 My4KGame 写完

手册第 4 章给了 `NoteData / GameManager / NoteController / NoteSpawner` 四个脚本，但只到"能掉音符"为止。这一步补齐了"能当作品交出去"的部分：

| 模块 | 内容 |
| --- | --- |
| 判定 | 四级判定 PERFECT ±40 / GREAT ±80 / GOOD ±120 / MISS >140（**毫秒**，不是像素） |
| 节奏 | `AudioSettings.dspTime` + `PlayScheduled` 提前排程，`SongTime` 做平滑 |
| 计分 | 连击、准确率、评级、最高分保存 |
| 流程 | 选曲 → 倒计时 → 游玩 → 暂停 → 结算 |
| 其他 | 音画校准、对象池、自动演示、编辑器自检 |

两个关键决定，后面所有功能都依赖它们：

1. **判定只看时间戳**：谱面加载时把拍号一次性烘成 `JudgeTimeMs`，之后永不修改；
2. **视觉与判定分离**：屏幕位置只在 `ScrollSpeedTrack.SecondsAheadToY` 里算，判定从不读坐标。

验证：菜单 5 自检全绿；菜单 9 真跑一局 4 音符测试谱面，判定全 PERFECT。

## 3. 需求：流速可调，但判定速度不变

> **我**：（长需求文档）在音游中，玩家调整"音符下落流速/视觉流速"时，不得改变音符的判定…

落地成三个文件，职责严格分开：

| 文件 | 职责 |
| --- | --- |
| `ScrollSpeedState` | 全局唯一数据源：1.00~10.00、步长 0.25、持久化、变更事件 |
| `ScrollSpeedTrack` | 把数值映射成"一屏几秒"：`系数 = 2^(2×(数值−5.50)/4.50)` |
| `NoteData.JudgeTimeMs` | 判定时间，**只由谱面和 BPM 决定**，调速不碰它 |

映射实测：

| 数值 | 系数 | 一屏时间 |
| --- | --- | --- |
| 1.00 | ×0.25 | 8.00 s |
| 5.50 | ×1.00 | 2.00 s |
| 10.00 | ×4.00 | 0.50 s |

验证（真跑三档流速各一局）：同一击打偏移在 0.5×/1×/2× 下判定结果完全一致，且 `judgeTimeMs` 一个毫秒都没变。

## 5. "你确定改好了吗" → 真正的 bug：委托不会被序列化

> **我**：你确定你修改好第一个任务了吗 我注意到你并没有按照我的要求完成 请你认真完成仔细检查

这次挖到了本项目最隐蔽的一个 bug：

```csharp
// TapRepeatButton 里
private Action _action;          // ← Unity 不序列化委托！
```

按钮是编辑器里生成并**存进场景**的，回到运行时 `_action` 是 `null`；而 `EnsureSpeedCard()` 看到卡片已存在就直接 `return`，没有重新 `Bind` → **点了等于没点**。

修法：每次进游戏都用路径把按钮取回来重新绑：

```csharp
private void BindSpeedCardArrows()
{
    speedMinusArrow = FindTapButton("SpeedCard/Tap◀", speedMinusArrow);
    speedPlusArrow  = FindTapButton("SpeedCard/Tap▶", speedPlusArrow);
    if (speedMinusArrow != null) speedMinusArrow.Bind(() => NudgeSpeed(-ScrollSpeedTrack.Step));
    if (speedPlusArrow  != null) speedPlusArrow.Bind(()  => NudgeSpeed(ScrollSpeedTrack.Step));
}
```

并且加了一条**按钮点击链路探针**（冒烟测试里），把"点击"拆成四段分别验证：

```
EventSystem 在不在 → 射线能不能命中 → 回调有没有被调用 → 数值有没有变
```

> 教训：**只要是运行时用代码建的 UI，回调就必须在运行时重绑**。这条后来救了一次（第 7.3 节）。

> **我**：和我协作的人制作好了 我要从 github 上 git 下来看看效果 我要怎么做
> **我**：我注意到这个谱面是不是存在一些问题…在 world's end blackbox 的 expert 谱面中出现了
> hold 音符持续时同轨道出现了新的 tap 音符…并且 hold 音符的交互逻辑存在问题 玩家无法直观感受到
> 这个音符是在被自己按着的…

协作方（Sice54546）交付了：暂停弹窗、结算按钮修复、**歌曲选择界面**、**Hold 长按机制**、两首新歌与曲绘。
拉下来实测后，有三个必须修的问题。

### 7.1 谱面冲突：86 处（协作方的谱面生成有缺陷）

写了个体检脚本扫全部 13 张谱：

| 谱面 | 冲突 | 同轨最小间距 |
| --- | --- | --- |
| WorldsEndBLACKBOX_Expert | 48 | **25 ms** |
| WorldsEndBLACKBOX_Hard | 15 | 25 ms |
| InYourBlueEyes_Expert | 8 | -1 ms |
| InYourBlueEyes_Hard | 3 | -1 ms |

为什么是致命的（不是难度问题）：

```csharp
// NoteSpawner.ResolvePress 第一行
if (_held[lane] != null) return Judgement.None;   // 按住期间，这条轨道的按键直接被吞
```

谱面在那儿放 tap，玩家怎么按都是空打 → 必 MISS。

修法：`tools/chart_tools.py --repair`，**只挪轨道，不删音符，时间轴零改动**（采音不动）。结果 86 → 0。

### 7.2 Hold 没有"被按住"的反馈

协作方只把音符"头"停在判定线上，全程没有任何光效。加了事件 + 三处表现：

```csharp
// GameManager
public event Action<int> HoldStarted;
public event Action<int> HoldEnded;
```

- 轨道常亮 + 呼吸（`LaneView.SetHeld`）
- 判定线光晕脉动 + 每 0.18 s 补一次**和 tap 完全一样**的扩散光环
- 音符本体提亮、尾条变亮；松手瞬间全部熄灭

### 7.3 按钮又点不动了（选择界面的遮挡）

协作方新加的选曲界面 `SongPanel` 是**全屏 + `raycastTarget=true`**，把右侧设置栏整个盖住，射线命中的是面板不是按钮。

修法：面板只占左侧，右侧留 640 px 给设置栏：

```csharp
songPanel.offsetMax = new Vector2(-SettingsColumnWidth, 0f);   // 640
```

### 7.4 顺手把 Expert 的键型排了一遍

Expert 的连续单点按 **交互 / 梯子 / 楼梯** 重排（时间轴不变，只改轨道）：

- 交互 `0 1 0 1`、梯子 `3 2 1 0`、楼梯 `0 1 2 3 2 1`
- 段内不跨 Hold、不撞双押；目标轨道被 Hold 占用就退化成挑空轨

验证：冒烟测试 **103 项 0 失败**，含"射线首位命中就是 ▶ 按钮""Hold 开始/结束事件成对""按住时 LaneView.IsHeld"。

## 8. Master 难度：三首各一张超密谱

> **我**：我觉得可以给每首歌再加一个 master 大师难度 这个难度下采音要特别密集
> 几乎没有整个屏幕都没有音符的休息段 请你再给他们写一个谱面

生成器 `tools/make_master.py`，原则：**不动时间轴，只加密**。

| 步骤 | 做法 |
| --- | --- |
| ① 采音锚点 | 直接用同曲 Expert（Neon Pulse 用 Hard）的全部时间戳 |
| ② 真实音头 | 有 WAV 的曲子额外做频谱通量 onset 检测（纯 numpy） |
| ③ 网格加密 | 锚点前后 16 分 + 全曲 8 分 + 兜底 16 分 |
| ④ 密度封顶 | 「最近 3 秒已放音符数 / 3」达到目标就不再塞 |
| ⑤ 补洞 | 任何超过 600 ms 的空档用 8 分补上 |
| ⑥ 键型 | 交互/梯子/楼梯每 6 个音换一次，小节首随机对切双押 |

结果：

| 曲目 | 音符数 | 密度 | 最大空档 |
| --- | --- | --- | --- |
| Neon Pulse | 411 | 5.87 音符/秒 | 375 ms |
| World's end BLACKBOX | 1245 | 7.98 音符/秒 | 580 ms |
| in your blue eyes | 1374 | 6.43 音符/秒 | 517 ms |

踩坑记录（密度算法错了三次，都是我自己写错）：

1. 用"优先级顺序"比较间距 → 大量候选被误判丢弃，密度只有 3.9/秒；
2. 密度统计只算"过去的半窗"却除以整窗宽度 → 上限被放大一倍，密度飙到 12.6/秒（不可玩）；
3. 统计时把**未来**的锚点也计入了 `len(accepted) - lo` → 几乎全部候选被拒。

最终版本按「时间顺序 + 最近邻间距 + 3 秒窗口局部密度」才正常。

## 10. 如果重来一次，我会先做这 8 件事

1. **先定"判定归时间、视觉归流速"**，否则后期所有功能都要返工；
2. **UI 回调永远在运行时重绑**（`Action` 不序列化），场景里存下来的按钮回调是 `null`；
3. **动态 UI 的层级和遮挡要显式管理**（全屏面板 + `raycastTarget` 是最常见的"点了没反应"）；
4. **谱面必须有结构校验**（Hold 期间同轨不得有音符、结束后留 140 ms、同刻同轨不重复）；
5. **自动化验收要能真跑**：自检（无头）+ 冒烟（真播放），比"我觉得没问题"可靠；
6. **测试要复位持久化状态**（校准值存在 PlayerPrefs，上一次跑完会让下一次全空打）；
7. **交接时先跑一遍体检再玩**：协作方交付的谱面里 86 处冲突，靠体检脚本 10 秒就能发现；
8. **每次改动都写清楚"验证数据"**（多少项检查、几个冲突、偏差几毫秒），复盘时全靠这些数字。
